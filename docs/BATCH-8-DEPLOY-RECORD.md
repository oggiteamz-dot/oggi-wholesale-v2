# Batch 8 — Deploy Record
**Catalog UX upgrades: grid-level search/filter/sort, low-MOQ filter, tiered-price nudge in the cart itself, trust/guarantee messaging · 11 Aug 2026**

## What was built
- **`migrations/013_v2_catalog_ux_settings.sql`**: adds `low_moq_threshold` (int, default 12), `trust_message`, `return_policy`, `payment_terms` to `v2_wholesalers` (the v2-owned mirror table from Batch 5 — never touches v1's real `wholesalers`). All nullable/defaulted so the 4 real wholesalers needed no backfill.
- **`js/data/wholesaler-settings.js`** (new): `getWholesalerSettings`/`updateWholesalerSettings` — the write path behind the new wholesaler Settings screen.
- **`js/data/catalog-filter.js`** (new): pure, DOM-free filter/sort logic (`defaultCatalogFilters`, `distinctColorsAndSizes`, `filterAndSortCatalog`) — search (name + SKU), colour multi-select, size multi-select, in-stock-only, low-MOQ-only (against the wholesaler's own configurable threshold, not a hardcoded number), and four sorts (newest, price asc/desc, name). Kept separate from the DOM-rendering toolbar specifically so it could be unit-tested directly (see Verification).
- **`js/components/catalog-toolbar.js`** (new): the actual search/filter/sort bar — search input, colour swatches, size chips, two toggle checkboxes, a sort dropdown, and a live "N of M products match" count. Colour/size options are derived from the real catalog passed in, never a static list, so a wholesaler with 3 colours never sees 20 dead chips.
- **`js/components/trust-badges.js`** (new): three generic "verified wholesaler / real-time inventory / secure order submission" badges (compact strip on the catalog grid) plus a full card on the cart showing the wholesaler's own payment-terms/return-policy/trust-message copy **only when they've actually filled it in** — never a fabricated default that would misrepresent a real policy.
- **`js/data/catalog.js`**: `getWholesaler` now also selects the four new settings columns — since every buyer page already calls `getWholesaler` once, this needed no extra query.
- **`js/data/cart.js`, `js/components/product-card.js`, `js/data/orders.js`**: cart lines now carry `productId` (additive field) so the cart view can compute the same cross-colourway aggregate the product card already used for tiered pricing (Batch 6). Reorder call sites also pass it through.
- **`js/views/buyer.js`**: `dashboard()` now renders the toolbar above the grid and re-renders client-side on every filter change (no network round trip per keystroke — filtering runs against the catalog already fetched once). `cartView()` now fetches pricing tiers for the products actually in the cart and shows a live "Add N more of this product to unlock $X/ea" nudge under each line — the same feedback the product card already gave, now also visible while editing quantities directly in the cart. The cart also gets the full trust/guarantee card right above the submit button.
- **`js/views/wholesaler.js`**: the `/wholesaler/settings` route, previously a placeholder, is now a real form for the low-MOQ threshold and the three trust-card text fields.

## A bug caught before shipping
While wiring the toolbar into `dashboard()`, the `onChange` callback (`renderGrid`) needed to call `toolbar.setResultCount(...)`, but `renderCatalogToolbar` originally fired an initial `onChange` synchronously during its own construction — before the `const toolbar = renderCatalogToolbar(...)` assignment had completed. That's a real temporal-dead-zone bug: the very first call into `renderGrid` would have thrown `ReferenceError: Cannot access 'toolbar' before initialization` the instant the buyer opened the catalog. Caught by re-reading the wiring before testing, not by the test itself. Fixed by removing the toolbar's auto-emit-on-mount behaviour entirely — it now only calls `onChange` on real user interaction, and callers render their own initial unfiltered grid via `defaultCatalogFilters()` right after construction. Documented as a caller-facing contract in the component's own doc comment so a future batch doesn't reintroduce the same ordering hazard.

## Verification
This sandbox's browser still can't reach Supabase (unchanged since Batch 2), so as with every prior batch, backend correctness was verified directly against the live database via curl: added the four new columns' full round trip (PATCH `low_moq_threshold`/`trust_message`/`payment_terms`/`return_policy` on wholesaler `mg`, confirmed persisted, reverted to defaults). Confirmed real catalog data shape (colours/sizes/moq_qty) matches what the new filter logic expects.

For the client-side filter/sort/toolbar logic specifically — the part that can't be verified via curl since it never touches the network — this batch went further than a plain "no thrown errors" pass: the local Playwright sandbox loaded the real `catalog-filter.js` and `catalog-toolbar.js` modules directly (via dynamic `import()` inside the page) against a fabricated 3-product catalog and asserted actual results, not just absence of crashes — search by name, search by SKU substring, colour filter, size filter, in-stock-only, low-MOQ-only against a real threshold, all four sort orders, and a combined filter that correctly returns zero results. Also drove the real toolbar DOM (typed into the search box, clicked the low-MOQ checkbox) and confirmed `onChange` fired with the right filter state each time, and did NOT fire during construction (confirming the TDZ fix holds). Separately, a route-navigation pass across every buyer route (catalog/cart/orders/favourites/suppliers) and every wholesaler route (dashboard/products/orders/inventory/settings) confirmed zero thrown JS errors (`pageerror` events), including the new Settings screen.

To exercise the cart's tiered-price nudge against real data (no tiers exist in the live DB right now — all Batch 6 test tiers were cleaned up after that batch shipped), a temporary real tier (5+ units → $18/ea) was inserted for a real `mg` product, a real stock reservation made via `v2_reserve_stock` for 2 units of one of its variants, and a cart line seeded via `localStorage` referencing that reservation + the product's id. All temporary test data (the reservation, the tier) was released/deleted afterward and confirmed clean via a final curl check.

## Known gaps / explicitly not done in this batch
- The low-MOQ filter compares against the product's first-order `moqQty`, not the per-buyer reorder threshold (`moqReorderQty`) — the grid-level filter runs before the per-card reorder distinction is meaningful to show, so it uses the same number every buyer sees on a first look. The product card itself still shows the correct reorder-aware minimum.
- Every real product in the live catalog currently has `moq_qty = 1` at the product level (higher MOQs so far were only set at the SKU/variant level in Batch 6/7 testing), so the "Low MOQ only" filter is a true no-op against today's real data until a wholesaler sets a real product-level minimum above their threshold — correct behaviour, not a bug, just not yet visibly different from "off" on the current demo data.
- The wholesaler Settings screen only covers the four Batch 8 catalog-UX columns. Broader settings (branding, locations, notifications) stay out of scope rather than being half-built.
