# Batch 7 — Deploy Record
**Prepack / ratio-pack selling: one-click bundle units, sell-through-informed ratio suggestions · 11 Aug 2026**

## Design choice worth recording
A pack has to collapse to ONE cart/order line ("2x Boutique Pack – Style ABC, Blue") per Research 3's explicit WhatsApp-native requirement, but real inventory still has to move per real SKU. Rather than build a second, parallel inventory pathway for packs, this batch reuses the existing variant-level reservation/ledger system from Batch 1 completely unchanged — each pack component reserves and decrements stock through the exact same RPCs every plain line uses. The only new thing is a `pack_line_id` shared across a pack's component `v2_order_items` rows, used purely to re-group them back into one display line when reading order history. This means Batch 7 adds zero new ways to get inventory wrong — it only adds a display-grouping layer on top of machinery that's already been through six batches of testing.

## What was built
- **`migrations/011_v2_prepack_schema.sql`**: `v2_pack_definitions` (product + optional colourway, name, optional flat price) and `v2_pack_components` (variant + qty per pack); `v2_order_items` gets `pack_id`/`pack_line_id`/`pack_qty` columns.
- **`migrations/012_v2_prepack_enforcement.sql`**: extends `v2_submit_order` (same signature, so this correctly `create or replace`s in place — no repeat of migration 010's duplicate-overload mistake) to write the pack columns onto order items, and to **skip the per-SKU MOQ check for pack-derived lines** — a pack's fixed composition (e.g. 1×S/2×M/2×L/1×XL) is deliberately allowed to include fewer units of one size than that SKU's own open-order minimum, because the pack itself is the sellable unit. Product-level MOQ still counts pack units toward the aggregate, so a pack still contributes real units toward the product minimum.
- **`js/data/prepacks.js`** (new): `listPacksForProduct`/`listPacksForProducts` (single vs. batch, same pattern as Batch 6's pricing context), `createPack`, `archivePack`, `getPackById` (for reorder — re-fetches CURRENT composition/price rather than a stale snapshot), `suggestPackRatio` (real sell-through-informed ratio: sums actual order-history qty per variant and reduces to the smallest whole-number ratio via GCD; falls back to an even ratio when there's no order history yet — the "always keep a fallback" principle from Research 3 applied to the suggestion algorithm itself, not just the buyer-facing UX), `groupPackLines` (re-collapses a flat order-item list back into pack display lines, shared by both buyer and wholesaler order history).
- **`js/data/cart.js`** (extended): `addPack`/`updatePackQty`/`removePack` — a pack line reserves stock for every component in one call and rolls back every reservation made so far if any component fails, so a pack is never partially reserved; `clear()` and `submit()` updated to handle both line shapes, with pack lines expanding into one payload entry per component at submit time.
- **`js/data/orders.js`**, **`js/data/wholesaler-orders.js`** (extended): fetch the new pack columns and apply `groupPackLines` before returning.
- **`js/components/product-card.js`** (extended): an "Available packs" section per product — qty stepper, one-click "Add pack", always shown alongside (never instead of) the existing open per-size stepper, matching Research 3's explicit "always keep the hybrid path" guidance.
- **`js/views/buyer.js`** (extended): fetches packs for the whole catalog grid once per load; cart view renders pack lines as a single row with in-place qty editing (still release-then-reserve under the hood); order history and the reorder button both handle pack lines correctly (reorder re-adds at the pack's *current* composition/price via `getPackById`, not a stale copy).
- **`js/views/wholesaler.js`** (extended): a "Packs" panel per product — lists existing packs with archive, and a create-pack form with a "Suggest ratio from sell-through" button that pre-fills the per-SKU quantity inputs.

## Verification
Direct-REST verification against the live database (browser-can't-reach-Supabase limitation unchanged since Batch 2): created a real pack (2× size 38 + 3× size 40 of Denim Utility Jacket), deliberately set the size-38 SKU's own MOQ to 10 (higher than the pack allocates), then confirmed (1) ordering the pack succeeds and both resulting `v2_order_items` rows correctly carry the shared `pack_id`/`pack_line_id`/`pack_qty` and the right per-line prices/subtotal: (2) a **plain** (non-pack) order of the same SKU at the same low quantity is still correctly rejected by its SKU MOQ — proving the bypass is scoped to pack lines only, not a blanket MOQ hole. Also verified every new query shape directly (`listPacksForProduct`'s nested variant join, `getPackById`, `suggestPackRatio`'s source query). All test data cleaned up afterward. Local Playwright structural pass across buyer (catalog/cart/orders) and wholesaler (products/orders): zero thrown JS errors.

## Known gaps / explicitly not done in this batch
- `suggestPackRatio` currently has no real order history to draw from (all test orders from every batch's own verification were deliberately cleaned up, and no real production orders exist yet in this build), so it will show the even-ratio fallback in practice until the wholesaler has real sell-through data — that's correct, honest behaviour per its own design, not a bug, but worth knowing so the "suggested" ratio isn't mistaken for a proven one on day one.
- No UI to edit an existing pack's composition after creation — only create-new and archive. A wholesaler who wants to change a pack's ratio has to archive it and create a new one. Fine at current scale.
- Packs are always product-scoped to one product; there's no cross-product bundle (e.g. one pack containing two different styles) — not called for by the research doc's prepack/ratio-pack framing, which is specifically about size-ratio bundles within one style.

## Status: Prepack/ratio-pack selling — one-click chat-orderable bundles, sell-through-informed ratio suggestions with a real fallback, and the mandatory "build your own mix" open-stepper path preserved alongside — is DONE and verified against live data, reusing the existing inventory ledger with zero new stock-integrity risk.
