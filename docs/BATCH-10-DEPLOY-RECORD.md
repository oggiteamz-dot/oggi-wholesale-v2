# Batch 10 — Deploy Record
**Mobile barcode receiving/picking · 11 Aug 2026**

## A real finding that shaped this batch's design
Before building "picking," I checked the real `v2_submit_order` function directly (not assumed) to see what state stock is actually in at each point in the order lifecycle. Finding: `v2_submit_order` already calls `v2_confirm_reservation` per line at the moment a buyer submits an order, which converts the reservation straight into a real `'sale'` stock decrement. **Stock is already fully decremented the instant an order exists** — there's no later point where "picking" would decrement it again. So "picking" in this system can't honestly be another inventory-mutation step; it has to be a fulfillment-VERIFICATION checklist (did the physical units for this order actually get pulled and packed?) layered on top, never touching `v2_inventory_balances`/`v2_inventory_movements` again. That's what got built — `v2_order_pick_items` is a pure checklist against the order's own real `v2_order_items` rows.

## What was built
- **`migrations/016_v2_mobile_ops_schema.sql`**: `barcode` added to `v2_product_variants` (nullable, unique when set — a real scannable barcode/UPC is often a different string from the internal SKU, and receiving/picking fall back to matching the SKU itself when no barcode has been assigned yet, so the feature works immediately with zero setup). `v2_order_pick_items` — one row per real order item, `expected_qty`/`picked_qty` with a check constraint that hard-blocks over-picking at the database level even if a client miscalculates.
- **`migrations/017_v2_picking_enforcement.sql`**: `v2_start_order_pick` (idempotently creates the checklist for an order), `v2_scan_pick_item` (atomic "one physical unit just got scanned" — row-locked, `+1` per call, matching how a picker actually works: one scan per unit placed in the box, not a typed quantity), `v2_undo_pick_item` (for mis-scans).
- **`js/data/picking.js`, `js/data/barcode-lookup.js`** (new): thin wrappers around the RPCs/lookups above.
- **`js/data/pricing-admin.js`** (extended): `setVariantBarcode`, and `getProductPricing` now also returns each variant's barcode.
- **`js/views/wholesaler.js`**: the "Pricing & MOQ" panel's per-SKU row gained a barcode input; the Orders list gained a "Scan to pick" link on confirmed/shipped orders (additive — the existing "Mark shipped" button is untouched, so a wholesaler who doesn't use scan-picking loses nothing).
- **`js/views/mobile-ops.js`** (new): two dedicated mobile-first screens — **Scan to Receive** (scan/type a code, see the matched SKU + current stock, confirm a qty, optional collapsible landed-cost fields, reuses `receiveStock`/`recordReceiptCost` from Batches 3/9 unchanged) and **Scan to Pick** (per-order checklist, scan-to-increment each line, per-line Undo, a "Mark fully picked & shipped" button that's disabled until every line is complete and then calls the existing `advanceOrderStatus`).
- **Scanning mechanism**: a plain autofocused text input that captures whatever a hardware barcode scanner types (virtually all warehouse barcode scanners act as a fast keyboard + trailing Enter — this needs no camera, library, or permission and is what most production warehouse web tools actually rely on). A `BarcodeDetector`-based camera-scan button is offered as a fully feature-detected, defensively-wrapped progressive enhancement on top — never required, never blocks the primary path.
- **`js/lib/nav-config.js`, `js/app.js`**: new "Scan to Receive" nav item; `registerMobileOpsRoutes` wired in alongside the other route registrars.

## A real bug caught and fixed before shipping
The first draft of `v2_scan_pick_item`/`v2_undo_pick_item` resolved a scanned code with `select ... where barcode = p_code union all select ... where sku = p_code limit 1` intending to prefer a barcode match. `union all` does not reliably order its combined rows — a `sku` match could win over a real `barcode` match (or vice versa) depending on the planner, silently breaking the documented "barcode first, SKU fallback" precedence for any variant unlucky enough to have both a barcode collision risk and a matching SKU string elsewhere. Rewritten as two explicit sequential lookups (check barcode; only fall through to SKU if that returned nothing) before ever running it against real data.

## Verification
Backend correctness verified directly against the live database via curl (browser-can't-reach-Supabase limitation unchanged since Batch 2):
- **Barcode uniqueness**: assigned a real barcode to one SKU, confirmed assigning the same barcode to a different SKU fails with a real Postgres `23505` uniqueness violation (not a silent overwrite).
- **Full pick lifecycle against a real order**: reserved and submitted a real 2-line order (3× one SKU, 2× another), started the pick checklist, scanned the barcoded SKU three separate times and confirmed `picked_qty` incremented by exactly 1 per call, confirmed a 4th scan of the same (now fully-picked) SKU correctly errors with `"Already fully picked for this SKU on this order"`, confirmed scanning a SKU that belongs to this wholesaler but NOT this order correctly errors with `"This SKU is not part of this order"`, confirmed scanning a completely unrecognized code errors with a clear `"No SKU or barcode matches..."` message, confirmed the SKU-fallback path works for the second line (which had no barcode assigned), and confirmed Undo correctly decrements and a re-scan correctly re-completes the line.
- **Cleanup surfaced a real, pre-existing (not introduced by this batch) RLS characteristic**: a direct `DELETE` against `v2_orders` via the anon key returned `204` but silently deleted nothing — `v2_orders` only has `SELECT`/`UPDATE` policies, no `DELETE` policy, so the anon role can't delete orders at all (inserts only happen through the `SECURITY DEFINER` `v2_submit_order` RPC, which bypasses RLS). This is actually sound design — orders shouldn't be client-deletable for audit-trail integrity — so it was left exactly as-is; test cleanup used the Supabase admin SQL path instead of the anon REST API for this one step. All test data (the order, its cascaded pick items, the temporary barcode, and every touched stock balance) was fully removed/restored and confirmed via a final read-back.

A local Playwright structural pass confirmed zero thrown JS errors across every wholesaler route (including the two new mobile-ops screens and a pick-view visit with a nonexistent order id) and every buyer route — no regressions. As with every batch since Batch 2, the actual data-dependent rendering of the two new screens (the matched-SKU card, the pick checklist) can't be exercised in this sandbox's browser since it can't reach Supabase; that logic is the same code paths already proven correct against live data via curl above, and the page-header-render-before-the-hang was confirmed to be the same "stuck on await" behavior seen in every prior batch, not a new failure.

## Known gaps / explicitly not done in this batch
- Camera-based scanning (`BarcodeDetector`) is implemented but could not be exercised in this sandbox — headless Chromium has no camera and `getUserMedia` requires a real permission grant. It's defensively feature-detected and wrapped so its absence/failure never blocks the primary keyboard/hardware-scanner path, which IS the one verified here and the one that works with any existing barcode scanner hardware without needing a camera at all.
- Picking is per real `v2_order_items` row (per real SKU), not re-grouped by pack (Batch 7) the way order history display is — a picker physically still has to pull each component SKU from its own shelf location regardless of how the order groups for display, so this is the physically-correct unit to checklist against, not a gap, but worth noting it looks different from the buyer/wholesaler order-history pack grouping.
- No barcode label printing/generation — a wholesaler assigns their own existing barcode/UPC values to SKUs (or a self-chosen internal warehouse label) but this batch doesn't generate or print anything.
