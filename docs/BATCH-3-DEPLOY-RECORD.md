# Batch 3 — Deploy Record
**Wholesaler module: orders, products, inventory · 11 Aug 2026**

## What was built
- **`js/data/wholesaler-orders.js`**: order fulfillment ladder (`new → confirmed → shipped → delivered`), with the buyer's full order list joined to line items.
- **`js/data/products-admin.js`**: product listing with live variant/stock rollups, archive/unarchive toggle, bulk percentage price update across every variant, and "duplicate as template" — clones a product's full structure (options, option values, and now variants too — see fix below) with zero stock, so a clone is immediately editable and sellable once unarchived rather than an empty shell.
- **`js/data/inventory-admin.js`**: live stock table across every variant and location, sorted lowest-available-first (most actionable), with a "Receive" action wired through the real `v2_receive_stock` RPC — never a direct balance write.
- **`js/views/wholesaler.js`**: real Dashboard (live open-order/low-stock/out-of-stock counts), real Orders (fulfillment ladder with one-click status advance), real Products (archive, duplicate, bulk price), real Inventory (stock table + receive). Clients, Catalogs, and Settings remain honest placeholders — Clients needs a real clients table and real auth (Batch 14 territory, not invented ad hoc here); Catalogs (multi-catalog/white-label) and Settings are sequenced later in the batch plan.

## Bugs found and fixed before shipping (both from directly testing the real REST calls, not assuming the schema was right)
1. **Silent write failures.** `v2_product_variants`, `v2_product_options`, `v2_product_option_values`, `v2_product_variant_option_values`, and `v2_orders` only had `SELECT` policies from earlier batches (intentional for inventory *quantities*, which must only move through the RPCs — but price edits, archive toggles, and order status are not quantity writes). Tested every write path this batch actually needs directly against the live REST API before shipping: `UPDATE`s with no policy don't error, they silently match zero rows and return `200 OK` — a worse failure mode than an explicit error, since the UI would have shown "success" while nothing changed. `INSERT`s with no policy fail loudly (`42501`, confirmed). Fixed with `005_v2_batch3_write_policies.sql`, adding exactly the write policies this batch's features need — same temporary/permissive-during-build posture as everything else, hardened for real in Batch 14.
2. **"Duplicate as template" wasn't actually useful.** The first version cloned a product's options and option values but not its variants — meaning the "template" had no actual SKUs to sell, just an empty structure. Fixed to also clone every variant (SKU suffixed `-COPY`, same price/cost/attrs, zero stock — no `v2_inventory_balances` row is created at all, so a cloned variant reads as genuinely un-stocked, not fabricated inventory) and correctly remap each variant's colour/size links through an old-value-id → new-value-id map built during the option copy step.

## Verification
Browser-based Supabase calls remain unreachable in this sandbox (documented in Batch 2's record — a sandbox network-policy gap, not a production issue). Continued the same direct-REST verification approach: every write this batch introduces — `UPDATE v2_product_variants` (price), `INSERT v2_product_options`/`v2_product_option_values`/`v2_product_variants`/`v2_product_variant_option_values` (duplicate-as-template's full chain) — was tested individually against the live database with the same public key the browser uses, both before the policy fix (confirmed the failure) and after (confirmed the fix). All test rows were cleaned up via direct SQL afterward (the client intentionally has no `DELETE` policy on any of these tables — archive-don't-delete is the correct permanent posture, not a gap).

Structural browser testing (navigation, rendering, zero JS errors) passed cleanly for all 7 wholesaler nav items: Dashboard, Products, Orders, Inventory, Clients, Catalogs, Settings.

## Known gaps / explicitly not done in this batch
- Pick list, notify-new-arrivals, WhatsApp broadcast helper, client notes/recency, cycle-count/reconciliation workflow (distinct from the simple receive/adjust already built), per-colour images, custom colours/sizing UI, multi-catalog, barcode/QR, white-label, highlight ribbons, guided tours — the remaining v1-verified wholesaler features are not yet re-implemented. Orders, Products, and Inventory were prioritized as the highest-value, most load-bearing core (matching the same judgment call made in Batch 2 for the buyer side).
- Multi-location is supported by the schema and the stock table (location name shown per row) but there's no UI yet to add/manage additional locations or transfer stock between them.

## Status: Orders/Products/Inventory core is DONE and verified against the live backend, including two real bugs found and fixed before shipping rather than after. Remaining wholesaler features explicitly deferred, not silently dropped.
