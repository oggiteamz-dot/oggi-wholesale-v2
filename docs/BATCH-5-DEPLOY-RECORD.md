# Batch 5 — Deploy Record
**Owner/Admin module: cross-wholesaler dashboard, universal search, onboarding queue, exports, audit log · 11 Aug 2026**

## Real bug found during this batch's verification (fixed, not shipped)
While curl-verifying the new owner.js queries, `select * from wholesalers` under the app's real publishable (`anon`) key returned zero rows (`content-range: */0`) instead of the four real wholesalers. Checked v1's actual RLS policies directly: `wholesalers` has real, already-applied security — every policy (SELECT/INSERT/UPDATE/DELETE) is scoped to the `authenticated` role only, using `is_owner()`/`my_wid()` helpers against real JWT claims. v2 is still on the Batch 0 dev-auth stub (no real Supabase session, replaced for real in Batch 14), so it talks to Postgres as `anon` — every one of those policies evaluates to false for v2 right now, and a write returns `200 OK` with an empty array (0 rows matched, not an error) rather than failing loudly. Same silent-no-op failure class already found in Batches 1 and 3, just on a v1 table this time instead of a fresh v2 one.

This had been silently broken since **Batch 2**: `js/data/catalog.js`'s `getWholesaler()` and `listWholesalers()` — the buyer's brand/currency lookup and the entire Suppliers tab — have been querying `wholesalers` directly and returning `null`/`[]` this whole time. Not caught in Batch 2 or Batch 4's testing because those batches' curl checks focused on the tables each batch actually introduced, not on a pre-existing call site in a different file.

**Fix, not a workaround**: v1's `wholesalers` table and its real RLS are untouched — per the standing instruction, v1's schema and security posture stay exactly as they are. `migrations/008_v2_wholesaler_directory.sql` adds `v2_wholesalers`, a v2-owned mirror (wid, brand, name, currency, active) populated from a join against v1's real `wholesalers` table, restricted to the four wids already confirmed live via `wholesale_state.doc.wholesalers` (mg, omni, sq, w1785168930020 — the same real-roster set every migration this build has used, excluding orphaned test rows like `WS-001` and `w1784990095973` that have zero references anywhere). Permissive dev-mode RLS, same posture as every other v2_ table. `catalog.js` and `owner.js` were both updated to read `v2_wholesalers` instead of `wholesalers`; `setWholesalerActive` now writes `v2_wholesalers.active` instead of attempting (and silently failing) a write to v1's table — documented in code as a deliberate, revisitable choice once Batch 14 gives v2 real auth.

## Verification
Same direct-REST verification approach as every prior batch (this sandbox's browser can't reach the live Supabase API — see Batch 2's record). Curl-tested every query owner.js and csv-export.js issue against the live database: `v2_wholesalers` select (4 real rows, correct brand/currency), a real PATCH toggle + revert, `universalSearch` across all 3 tables with real matches (e.g. "mil" → Milano Garments), `listSignupRequests`/`reviewSignupRequest` (approved then reverted to pending), `logAudit` insert + `getAuditLog` read (test row cleaned up after), and all 3 CSV export source queries (`v2_products`, `v2_clients`, `v2_orders` — orders legitimately empty, no orders have been placed through v2 checkout yet). Also ran a local Playwright structural pass (this sandbox's own Chromium against its own localhost dev server, not the claude-in-chrome browser — that tool connects to a browser that can't reach this sandbox's localhost): all 6 owner nav items render, routes resolve, zero thrown JS errors (one harmless `favicon.ico` 404). Dashboard/Wholesalers/Onboarding show a stuck "Loading…" state in that specific test run because that browser can't reach Supabase's REST API either (the same documented sandbox-only network gap) — the underlying queries are proven correct via the curl pass above.

## Known gaps / explicitly not done in this batch
- Owner console access itself is still gated only by the Batch 0 dev-auth stub, same as every other role — real "only an actual owner can reach `/owner`" enforcement is Batch 14, by design.
- `reviewSignupRequest` approving a request does not yet provision the buyer an actual account/login — there's no real buyer auth yet for it to create (also Batch 14).
- No pagination on Universal Search or Audit Log (capped at 10 and 100 rows respectively) — fine at current data volume, would need real pagination before it matters.
