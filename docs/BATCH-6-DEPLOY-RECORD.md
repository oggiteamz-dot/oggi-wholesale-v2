# Batch 6 — Deploy Record
**Pricing & MOQ engine: tiered pricing, three-level MOQ, retail/margin display, negotiated "Your Price" · 11 Aug 2026**

## Real bug found and fixed while building this batch
While designing the checkout RPC to enforce the new pricing rules, I read the existing `v2_submit_order` (from Batch 2) and found it took `unit_price` straight from the client-supplied cart payload and wrote it to the order with **zero server-side verification** — any buyer client, buggy or malicious, could submit an order at any price it liked. Every other money/stock-affecting write in this build goes through an atomic, server-computed RPC specifically so the client is never trusted for the number that matters (the reservation/stock-decrement RPCs from Batch 1 are the model) — pricing had quietly been the one exception, unnoticed because nothing before this batch needed to compute a price server-side. `v2_submit_order` is rewritten to recompute `unit_price` itself (override → tier → base) and ignore whatever the client sent; confirmed via curl that submitting a line with `"unit_price": 0.01` still charges the real price.

A second bug turned up immediately during curl verification: `create or replace function` with a **different parameter list** doesn't replace a function in Postgres — it silently creates an additional overload, which broke every RPC call with a PostgREST "ambiguous overload" error. Fixed by explicitly dropping the old 4-argument signature before creating the 5-argument one (now baked into the saved migration, not just fixed live). A related type issue (`bigint` aggregate qty vs. an `int` function parameter, which Postgres won't implicitly cast in a function-call context) was caught the same way and fixed by typing the helper function's parameter as `bigint`.

## What was built
- **`migrations/009_v2_pricing_moq_schema.sql`**: `moq_qty`/`moq_reorder_qty` on `v2_products`; `moq_qty`/`retail_price` on `v2_product_variants`; `order_min_qty`/`order_min_value` on `v2_wholesalers`; `client_id` added to `v2_orders` (needed for real reorder-detection and override resolution, replacing fragile buyer-label string matching for anything that actually gates behaviour); new `v2_pricing_tiers` (product-scoped, all-units) and `v2_client_price_overrides` tables. No data migration section — this is new-in-v2 functionality (Research 3), nothing to pull from `wholesale_state.doc`; real tiers/MOQs/overrides get entered going forward through the admin UI this batch also ships.
- **`migrations/010_v2_pricing_moq_enforcement.sql`**: `v2_effective_unit_price()` (override → tier → base) and a rewritten `v2_submit_order` that enforces SKU-level MOQ, product-level MOQ (aggregated across every colour/size, with a first-order-vs-reorder distinction based on real prior-order history), and order-level MOQ (qty and/or value) — any violation raises and aborts the whole submit, same atomicity guarantee the RPC has had since Batch 2.
- **`js/data/pricing.js`**: client-side mirror of the server's pricing/MOQ logic for instant cart feedback (`effectivePrice`, `tierForQty`, `nextTier`, `productMoqStatus`, `variantMoqStatus`, `marginPct`), plus `resolveClientId()` (matches a buyer's session label to a real `v2_clients` row, same string-matching precedent Batch 4's salesperson recency sort already established) and `getPricingContext()` (batch-fetches tiers + a client's overrides in one round trip).
- **`js/data/catalog.js`** (extended): variant/product rows now carry `moqQty`, `moqReorderQty`, `retailPrice`.
- **`js/data/cart.js`** (extended): `submit()` accepts and forwards `clientId`; the comment explains the server now ignores the `unit_price` it still receives.
- **`js/data/orders.js`** (extended): `getBuyerOrderedProductIds()` for real first-order-vs-reorder detection on the buyer side.
- **`js/components/product-card.js`** (extended): tier ladder shown near the price, MOQ badge, live "add N more to unlock $X/ea" and "add N more to meet the minimum" feedback as the buyer types a qty, MSRP + margin % shown when a retail price is set.
- **`js/views/buyer.js`** (extended): fetches pricing context + reorder set once per catalog load, resolves `clientId` at checkout, surfaces the server's real MOQ/minimum-violation message (not a generic failure) if submit is rejected.
- **`js/data/pricing-admin.js`** (new): wholesaler-side CRUD for product MOQ, tiers, per-SKU MOQ/retail price, and order-level minimums.
- **`js/views/wholesaler.js`** (extended): each product row gets a "Pricing & MOQ" panel (MOQ fields, tier list with add/remove, per-SKU MOQ + retail price mini-table); an order-level minimum card added to the Products view.
- **`js/data/client-pricing.js`** (new): CRUD for per-client negotiated "Your Price" overrides.
- **`js/views/salesperson.js`** (extended): each client row gets a "Manage pricing" panel to set/remove negotiated prices per SKU.

## Verification
Direct-REST verification against the live database (this sandbox's browser still can't reach it — see Batch 2's record), covering every enforcement path with real requests against the real schema, then cleaning up: (1) base price with a client-sent `unit_price: 0.01` — server correctly charged the real $19.00; (2) product-level MOQ rejection below threshold; (3) all-units tiered pricing aggregated across two colourways — both lines correctly priced at the $15 tier once the combined 10-unit threshold was hit; (4) client override — correctly took precedence over both the tier and the base price; (5) order-level MOQ rejection; (6) reorder MOQ — a returning client was correctly allowed a lower reorder threshold; (7) SKU-level MOQ rejection. Also verified every new admin/picker query shape directly (`getProductPricing`'s three parallel queries, `getOrderMinimums`, `listVariantsForPicker`, `listClientOverrides`'s nested `v2_product_variants(...,v2_products(name))` embed) and a full write→read→delete cycle for a client override. All test data and mutations reverted afterward; the schema now holds only real, non-fabricated wholesalers/products/clients data with no tiers/overrides/MOQ overrides seeded (that's honest, not a gap — nothing existed in v1 to migrate for this feature). Local Playwright structural pass across buyer/wholesaler/salesperson: all routes render, zero thrown JS errors; the two new admin panels ("Pricing & MOQ", "Manage pricing") couldn't be click-tested end-to-end in this sandbox because the underlying product/client list queries hang on the same browser-can't-reach-Supabase limitation documented since Batch 2 — the panels' own queries are proven correct via the curl pass above.

## Known gaps / explicitly not done in this batch
- No UI yet to bulk-import tiers/MOQs across many products at once — each product's pricing panel is edited one at a time. Fine at current catalog size.
- The buyer-side `resolveClientId()` match is by exact `shop_name` == session label, same precedent as Batch 4's recency sort — a salesperson placing an order *as* a specific client (rather than the client logging in themselves) still isn't wired into any UI (that gap was already flagged in Batch 4 and remains open, now also relevant here since it's the cleanest way to guarantee overrides apply).
- Order-level minimums are wholesaler-wide only, not per-client — a wholesaler can't yet waive their own minimum for one negotiated client.

A real pricing-integrity gap dating back to Batch 2 was found and fixed as part of this batch, not left for later.
