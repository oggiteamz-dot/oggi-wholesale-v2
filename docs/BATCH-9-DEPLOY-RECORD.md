# Batch 9 — Deploy Record
**Inventory intelligence: landed cost tracking, reorder-point automation, kit/bundle SKUs, ABC-tiered cycle counting, GMROI/aging/sell-through reporting · 11 Aug 2026**

## Design choices worth recording
- **Kits vs. Batch 7's prepacks — deliberately two different mechanisms.** A prepack collapses to one order line at ORDER time but never exists as real on-hand stock, and is scoped to one product's own colourways. A kit here is pre-ASSEMBLED ahead of time into its own real, sellable, cross-product SKU (`v2_kit_definitions.kit_variant_id` is a normal `v2_product_variants` row — priceable, orderable, countable exactly like any other SKU). `v2_assemble_kit` is the only way component stock converts into kit stock, and it's built entirely out of the existing `v2_decrement_stock`/`v2_receive_stock` RPCs from migrations/001 — no new balance-mutation logic, same "reuse the already-tested ledger primitives" discipline Batch 7 established.
- **Landed cost is a side table, not a column on the ledger.** `v2_receipt_costs` links loosely to a specific receiving movement rather than living as a required column on `v2_inventory_movements` — most receipts (and every count correction/manual adjustment) have no freight/duty/other detail at all, so a side table with an optional link is more honest than a column that's empty on most rows.
- **ABC classification is derived live, never stored.** Same principle as Batch 7's sell-through ratio suggestion: caching a snapshot classification would go stale the moment new orders come in, so `getInventoryIntelligenceReport` recomputes each SKU's share of trailing revenue (and therefore its A/B/C tier) fresh on every call.
- **GMROI/aging are honestly-scoped approximations, disclosed as such** (see Known gaps) rather than presented as more precise than the underlying data supports.

## What was built
- **`migrations/014_v2_inventory_intelligence_schema.sql`**: `reorder_point`/`reorder_qty`/`lead_time_days` added to `v2_product_variants` (all nullable — no automation until a wholesaler opts in per SKU); `v2_kit_definitions` + `v2_kit_components` (cross-product kit definitions); `v2_receipt_costs` (landed-cost detail per receipt, soft-linked to `v2_inventory_movements` since that table's primary key is the composite `(id, created_at)` — almost certainly time-partitioned — so a plain FK to `id` alone isn't possible without altering that established core table's key structure, which this build does not do); `v2_cycle_counts` (physical count log, expected vs. counted, real variance).
- **`migrations/015_v2_kit_assembly_enforcement.sql`**: `v2_assemble_kit(kit_id, location_id, qty)` — atomically decrements every component (`movement_type='adjustment'`, since the table's own check constraint doesn't include a kit-specific type, disambiguated instead via `reference_type='kit_assembly'`) and produces the kit SKU's stock via `v2_receive_stock`. Any component with insufficient stock raises, which rolls back every decrement already applied in that call — verified directly (see Verification).
- **`js/data/landed-cost.js`** (new): `recordReceiptCost` (computes `landed_unit_cost = base cost + (freight+duty+other)/qty`, best-effort links to the actual receiving movement), `getLatestLandedCosts` (most recent cost entry per variant, falling back to the variant's own base cost when none exists).
- **`js/data/kits.js`** (new): `listKits`, `createKit`, `archiveKit`, `assembleKit`.
- **`js/data/inventory-intelligence.js`** (new): `getReorderSuggestions` (available ≤ reorder_point, sorted most-urgent first), `getInventoryIntelligenceReport` (per-variant trailing sales, GMROI, aging bucket, sell-through %, ABC tier), `getCycleCountSchedule` (ABC-tiered count frequency — A/30d, B/90d, C/180d — against real last-count history), `logCycleCount` (logs the count, then applies any variance through the SAME `adjustStock` the manual inventory screen already used since Batch 3 — never a second way to mutate balances).
- **`js/data/pricing-admin.js`** (extended): `getProductPricing` now also returns each variant's reorder settings; new `setVariantReorderSettings`.
- **`js/data/inventory-admin.js`** (extended): `getStockTable` now also returns each row's base `cost`, needed by the landed-cost receive flow.
- **`js/views/wholesaler.js`**: the existing per-product "Pricing & MOQ" panel gained a per-SKU reorder-point/qty/lead-time mini-table; the existing "Receive" flow in Inventory gained an optional (skippable) landed-cost prompt sequence; a new `/wholesaler/intelligence` page (added to the nav) with four sections — reorder suggestions with a one-click "Receive suggested qty", the GMROI/aging/sell-through/ABC report table, the cycle-count schedule with "Log count", and kit management (list/assemble/archive existing kits, create a new kit from existing SKUs).
- **`js/lib/nav-config.js`**: added the "Intelligence" nav item for the wholesaler role.

## Verification
Backend correctness verified directly against the live database via curl (this sandbox's browser still can't reach Supabase — unchanged since Batch 2):
- **Kit assembly, happy path**: created a real cross-product kit (1× Merino Crew Knit Midnight-Blue-36 + 1× Merino Crew Knit Sand-36, bundled under an unrelated Wool Overshirt SKU standing in as the kit's own SKU), assembled 2 kits, confirmed both components decremented by exactly 2 and the kit SKU's on-hand increased by exactly 2, with the resulting `v2_inventory_movements` rows carrying the right `movement_type`/`reference_type`.
- **Kit assembly, atomicity — two separate failure scenarios**: (1) requested 100 kits against a component with only 8 available — failed on the very first component, zero balance change; (2) requested 5 kits where the FIRST component had enough stock (8, needs 5) but the SECOND did not (3, needs 5) — confirmed the first component's decrement was rolled back too, not left partially applied. This is the real proof the "one plpgsql function body = one transaction" atomicity claim holds, not just the trivial single-component-failure case.
- **Landed cost**: received 10 real units, computed `landed_unit_cost = 13.00 base + (20 freight + 5 duty + 0 other)/10 = 15.50`, inserted and re-read back correctly.
- **Reorder-point automation**: set a real reorder point (20) above a variant's real available qty (18), confirmed the surfacing condition (`available <= reorder_point`) holds against real data.
- **Cycle counting**: logged a real count with a real variance (-2) and applied the correction through `v2_decrement_stock` with `movement_type='count_correction'`, confirmed the resulting on-hand matches the counted qty exactly.
- All test data (kit, components, receipt cost, cycle count row, reorder-point settings) was cleaned up and every touched balance restored to its exact original value, confirmed via a final read-back.

A local Playwright structural pass navigated every wholesaler route (dashboard/products/orders/inventory/**intelligence**/settings) and every buyer route (catalog/cart/orders) and confirmed zero thrown JS errors (`pageerror` events) — including the new Intelligence page and the extended Pricing panel/Receive flow.

## Known gaps / explicitly not done in this batch
- GMROI's "average inventory value" uses current on-hand × landed cost as a point-in-time proxy, not a true time-averaged inventory value over the period — a standard simplification when full lot-level cost history isn't tracked, but worth knowing it slightly overstates/understates GMROI versus a true period average depending on how stock moved during the window.
- Aging uses the most recent 'receive' movement per variant as the aging clock for ALL of that variant's current on-hand stock — it doesn't do true FIFO lot-level aging, so if older stock is still mixed in with a more recent receipt, this understates how old that older portion really is. A real lot-tracking system would need to attach a lot/batch id to each unit, which is a materially bigger change than this batch's scope.
- No kit disassembly (reversing an assembled kit back into its components) — only forward assembly. Noted as a fine gap at current scale, same as Batch 7's "no pack-edit UI" precedent.
- The cycle-count "Log count" and landed-cost receive flows both still use `prompt()`-based sequential input (matching this view's existing established pattern from Batch 3's Receive button) rather than a richer inline form — acceptable for now, a UI polish candidate for Batch 13.
